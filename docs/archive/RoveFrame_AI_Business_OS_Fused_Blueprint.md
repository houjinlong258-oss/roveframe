# RoveFrame AI Business OS — 融合技术方案

> 基于 Ultimate Blueprint 战略愿景 + 技术架构评审建议，融合产出的可落地方案。

---

## 一、战略定位（保留蓝图愿景）

**一句话定位**：RoveFrame 是中小企业的 AI COO——一个 24/7 理解业务运营、发现问题、推荐策略、执行任务的智能经营伙伴。

**核心哲学**（不变）：
- 数据 → 知识 → 智能 → 行动
- 用户不管理软件，用户通过 AI 管理生意
- 复杂性隐藏在后面，用户只看到洞察、建议和可执行动作

**与竞品的本质区别**：不是又一个 ERP / CRM / 自动化工具，而是架在所有系统之上的**智能层**。

├──────────┬──────────┬──────────┬──────────┬─────────────┤
│ AI 智能层 │ 知识层    │ 商业层    │ 沟通层    │ 分析层       │
│ Dify     │ Qdrant/  │ ERPNext  │ Chatwoot │ Metabase    │
│ + Agent  │ Supabase │ (或轻量   │          │             │
│ 推理引擎  │ Vector   │  替代)    │          │             │
├──────────┴──────────┴──────────┴──────────┴─────────────┤
│                  自动化执行层 (n8n)                        │
├─────────────────────────────────────────────────────────┤
│                  数据层 (PostgreSQL)                      │
└─────────────────────────────────────────────────────────┘
```

### 2.2 关键新增：RoveFrame Integration Layer（集成中枢）

这是上次评审中提出的核心建议，也是整个产品的**技术护城河**所在。

**职责**：
| 功能 | 说明 |
|------|------|
| 统一 API Gateway | 所有前端请求通过 Gateway 路由到对应子系统，用户无感知 |
| 数据同步引擎 | 各子系统间的数据一致性保障，定义 Master Source of Truth |
| 事件总线 | 子系统间通过事件解耦通信（如：新订单 → 触发 AI 分析 → 更新 Dashboard） |
| 认证中心 | 统一登录/权限，各子系统通过 Gateway 鉴权 |
| 审计日志 | 所有 AI 建议和操作留痕，满足安全合规 |

**技术实现建议**：
- 用 **Next.js API Routes** 或独立的 **Node.js/Python BFF** 作为 Gateway
- 事件总线初期可用 **PostgreSQL + 轮询** 或 **Redis Pub/Sub**，规模上来后换 Kafka
- 不要在 MVP 阶段引入完整 ESB，保持轻量

### 2.3 数据主权定义（解决数据一致性）

| 数据实体 | Master Source | 说明 |
|----------|--------------|------|
| 产品/服务 | ERPNext（或自建轻量模块） | 商品、价格、库存的唯一来源 |
| 订单 | ERPNext | 订单生命周期管理 |
| 客户 | Twenty CRM | 客户画像、跟进记录、Pipeline |
| 沟通记录 | Chatwoot | 所有客户对话的统一入口 |
| AI 知识 | Dify + Vector DB | 知识库、业务记忆、RAG |
| 业务分析 | Metabase | 报表和可视化 |
| 用户/权限 | RoveFrame Integration Layer | 统一认证 |

**同步规则**：
- 采用 **Event-Driven 单向同步**：Master 系统产生变更事件 → Integration Layer 消费 → 推送到需要该数据的子系统
- 冲突策略：Master Source 永远优先，下游系统不反向写
- 失败处理：重试 3 次 → 进入 Dead Letter Queue → 通知管理员

## 三、开源底座选型（融合建议）

| 蓝图选择 | 评审建议 | 融合结论 | 理由 |
|----------|---------|---------|------|
| ERPNext | 原方案用 Medusa.js | **MVP 阶段用轻量自建模块，Phase 2 接入 ERPNext** | ERPNext 功能全面但部署重（Python/Frappe 框架），MVP 阶段用不到 20% 功能。先自建产品+订单模块，验证业务后再接入 |
| Twenty CRM | ⚠️ 相对年轻 | **保留，但作为 Phase 1.5 接入** | MVP 先用简单客户表，CRM 需求明确后再接入 Twenty |
| Chatwoot | 新增 | ✅ **保留，Phase 1 接入** | 多渠道沟通是 AI COO 的核心触点，优先级高 |
| Dify | ✅ | ✅ **保留，Phase 0 就开始** | AI 是核心差异化，必须最早投入 |
| n8n | ⚠️ 学习曲线陡 | **保留，但 MVP 用简单脚本替代** | MVP 阶段自动化场景有限，用 cron + 脚本够用，Phase 2 再引入 n8n |
| Metabase | 新增 | ✅ **保留，Phase 1 接入** | 快速提供数据可视化，部署成本低 |

### 融合后的技术栈

```
Frontend:     Next.js 14+ (App Router)
Backend API:  Next.js API Routes (MVP) → 独立 Node.js/Python 服务 (Phase 2+)
Database:     PostgreSQL 16
AI Engine:    Dify (Agent + RAG + Workflow)
Vector DB:    Supabase Vector (MVP) → Qdrant (规模化)
Communication: Chatwoot
Analytics:    Metabase
Auth:         NextAuth.js / Clerk (MVP) → 自建 (Phase 2+)
Hosting:      Docker Compose (MVP) → Kubernetes (规模化)
```

## 四、AI COO Agent 设计（蓝图核心 + 工程细化）

### 4.1 Agent 架构

```
                    ┌─────────────────┐
                    │   AI COO Agent   │
                    │  (Orchestrator)  │
                    └────────┬────────┘
                             │
            ┌────────────────┼────────────────┐
            │                │                │
    ┌───────▼──────┐ ┌──────▼──────┐ ┌───────▼──────┐
    │ 分析 Agent   │ │ 执行 Agent   │ │ 沟通 Agent   │
    │ - 营收分析    │ │ - 内容生成   │ │ - 客服回复    │
    │ - 趋势预测    │ │ - 邮件草稿   │ │ - 主动通知    │
    │ - 异常检测    │ │ - 营销方案   │ │ - 多渠道分发   │
    └──────────────┘ └─────────────┘ └──────────────┘
            │                │                │
            └────────────────┼────────────────┘
                             │
                    ┌────────▼────────┐
                    │  Knowledge Brain │
                    │  (长期业务记忆)   │
                    └─────────────────┘
```

### 4.2 Knowledge Brain 实现

| 知识类型 | 存储方式 | 更新频率 |
|----------|---------|---------|
| 业务文档 | Vector DB (RAG) | 用户上传时 |
| 产品知识 | Vector DB + 结构化 | 产品变更时自动同步 |
| 客户偏好 | 结构化 DB + 向量索引 | 每次交互后更新 |
| 历史决策 | 结构化 DB + 摘要向量 | 每次决策后记录 |
| 运营经验 | Vector DB | AI 自动总结沉淀 |

### 4.3 AI 安全原则（来自蓝图 + 强化）

- **建议优先，执行需审批**：AI 默认只给建议，涉及资金/对外沟通/数据删除等操作必须人工确认
- **操作分级**：
  - 🟢 自动执行：数据查询、报表生成、内部分析
  - 🟡 一键确认：回复邮件、生成营销内容、调整定价建议
  - 🔴 强制审批：退款、删除数据、对外承诺、合同变更
- **全链路审计**：每次 AI 操作记录 input → reasoning → output → user action

## 六、首个行业选择（评审建议）

蓝图选择**餐饮**作为首个行业。评审建议重新考虑：

| 维度 | 餐饮 | 美容/美发 | 专业服务（律所/会计） |
|------|------|----------|-------------------|
| 客单价 | 低 | 中高 | 高 |
| 数字化意愿 | 中（竞品多） | 中高 | 中 |
| AI 价值感知 | 低（利润薄） | 高（营销驱动） | 极高（知识密集） |
| 竞品密度 | 极高（Toast, Square） | 中 | 低 |
| 付费意愿 | 低 | 中高 | 高 |
| 实施复杂度 | 中 | 低 | 中 |

**建议**：如果目标是快速拿到付费客户并证明 AI 价值，**美容/美发**或**专业服务**可能比餐饮更合适。但如果团队在餐饮行业有资源和人脉，餐饮仍然是可行的。

## 七、部署与运维（评审补充）

### MVP 阶段部署方案

```
推荐：单台 VPS (4C8G 起步) + Docker Compose

容器组成：
├── nextjs-app        (前端 + API)
├── postgres          (数据库)
├── dify              (AI 引擎，自带多容器)
├── chatwoot          (沟通中心)
├── metabase          (数据分析)
└── nginx             (反向代理 + SSL)

预估月成本：$50-100（VPS）+ $50-200（LLM API）

### 监控基础

- **应用监控**：Sentry（错误追踪）

- **业务监控**：Metabase 内置 Dashboard
- **AI 监控**：Dify 内置日志 + 自建审计表

## 九、核心风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 多系统集成复杂度 | 开发周期超预期 | 分阶段接入，MVP 用轻量自建替代重型开源 |
| LLM API 成本 | 利润率被压缩 | 分级调用（简单问题用小模型，复杂分析用大模型）；缓存常见问答 |
| 数据一致性 | 用户体验差 | 严格 Master Source 定义 + 事件驱动同步 |
| 客户获取成本 | 现金流压力 | 先做实施服务（$1K-$10K）养活团队，同时打磨产品 |
| AI 幻觉/错误建议 | 客户信任损失 | 建议+审批模式 + 全链路审计 + 渐进式放权 |
| 开源项目变动 | 技术债务 | 对每个开源依赖做抽象层，保留替换能力 |

## 十、产品原则（保留蓝图，补充技术原则）

### 产品原则
1. AI 应该简化复杂性，不增加复杂性
2. 商业老板应该用自然语言管理生意
3. 数据应该变成可执行的智能
4. 自动化必须安全可控
5. 产品应该通过记忆不断进化

### 技术原则（评审补充）
6. **集成层是产品**——子系统是零件，Integration Layer 才是 RoveFrame
7. **Master Source 唯一**——每个数据实体只有一个权威来源
8. **AI 建议优先，执行需确认**——除非明确授权自动执行
9. **轻量起步，按需升级**——不自建能用的开源就用开源，但保留替换能力
10. **可观测性优先**——从 Day 1 就有日志、监控、审计
